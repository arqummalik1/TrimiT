# TrimiT Mobile 1.1.0 Update Notes

This document explains the mobile application changes introduced on the `apple-fix` branch for version 1.1.0. It is written for future developers and AI agents who need to understand why the authentication, onboarding, roles, and booking flow work differently from version 1.0.2.

## Why this release exists

Version 1.0.2 required people to create an account before they could use the application and asked every new account to choose a role and complete the same large profile form. It also asked Apple users for information that Apple Sign In may already provide.

Version 1.1.0 changes the product to a guest-first experience. People can explore the marketplace before creating an account. Authentication is requested only when an action genuinely needs an account.

This release directly addresses the App Review concerns about mandatory login for public browsing and repeatedly collecting a person's name or email after Apple Sign In.

## New customer journey

1. A first-time user sees the redesigned introduction screens.
2. After the introduction, the user enters the public customer application as a guest instead of being forced into the login screen.
3. Guests can browse salons, search, use lists and maps, apply filters, and open salon and service details.
4. When a guest chooses an account-based action, the application remembers exactly what they were trying to do and opens authentication.
5. A normal new account is automatically created as a customer. There is no role-selection screen in the customer booking journey.
6. After successful email OTP, Google, or Apple authentication, the user returns to the original action instead of being sent to the home screen.
7. For a booking, the user confirms a valid contact number before availability is loaded and before any time slot can be held.

If authentication is cancelled, the user remains in the public browsing experience and can return to the salon or service they were viewing.

## Public guest access

The root navigation no longer treats authentication as the entrance to the whole application. A guest can use public customer discovery screens, including salon and service detail screens.

Guests do not see the signed-in customer tab bar. Discover remains the public home, and a discreet account/support action in its header opens authentication, salon-team entry, legal pages, and support. The Bookings and Profile tabs appear only after authentication. This avoids presenting empty personal destinations before the visitor has an account.

Account protection remains in place for actions such as:

- starting or completing a booking;
- viewing personal bookings;
- rescheduling a booking;
- writing a review;
- opening or editing the personal profile;
- starting salon-owner setup;
- claiming employee access.

The main navigation decision is implemented in `src/navigation/index.tsx`. Protected-action helpers are in `src/lib/authGate.ts`, and navigation outside React components is supported by `src/navigation/navigationRef.ts`.

## Safe return after authentication

The application now stores a typed pending authentication intent in `src/store/pendingAuthIntentStore.ts`.

Supported mobile intents are:

- customer booking;
- personal bookings;
- booking reschedule;
- writing a review;
- personal profile;
- owner onboarding;
- employee invitation claim.

The intent contains only the identifiers and values required for an approved destination. Arbitrary navigation routes are not accepted.

The pending intent:

- is persisted in device storage so a short app restart does not lose it;
- expires after 20 minutes;
- is validated again after being read from storage;
- is consumed only once after successful authentication;
- is cleared when invalid or expired;
- prevents repeated authentication and navigation loops.

## Apple, Google, email, and profile creation

The authentication store and service now use provider identity information when it is available.

- Apple full name and email are captured during the first authorization and saved immediately.
- Apple can return the name only on the first authorization. Later sessions recover it from Supabase user metadata when possible.
- Google profile metadata is handled through the same streamlined profile-bootstrap flow.
- The application does not ask Apple or Google users to enter their email again.
- A missing display name does not block access. The backend can resolve a provider name, derive a safe label from the email, or use a neutral fallback. The user can edit the profile later.
- Email OTP registration also automatically creates a customer profile unless an approved owner or employee intent is active.

The relevant implementation is in `src/store/authStore.ts`, `src/services/authService.ts`, and `src/repositories/authRepository.ts`.

## Account and data deletion

Version 1.1.0 adds a complete in-app account deletion flow rather than sending
people to a generic support form.

- Customer Profile and owner Settings both open the shared
  `src/screens/account/AccountDeletionScreen.tsx` review screen.
- The screen explains what will be removed for the current account role, shows
  the signed-in identity, and requires a final destructive confirmation.
- Apple-linked accounts open a fresh native Apple confirmation. The backend
  exchanges the returned authorization code and revokes Apple's refresh token
  before deleting the account.
- Google access is revoked through the native Google SDK after server deletion,
  when that SDK has an active grant.
- Successful deletion clears push registration, Supabase session data, React
  Query data, persisted authentication, and the local signed-in state.
- `https://trimit.online/delete-account` is the dedicated public web fallback
  for users without the app. Do not change this link back to `/contact`; Google
  Play requires a prominent external deletion resource.

The backend removes the Auth user, public profile, account-associated database
records, marketing/waitlist records matching the account email, and uploaded
owner service/staff images. Protected backend requests revalidate the live
Supabase Auth session on each short profile-cache miss, and successful deletion
evicts the local cache immediately, so a stale access JWT is rejected instead of
remaining usable until its normal expiry.

Release prerequisite: manually apply `database/63_account_deletion_integrity.sql`
in the production Supabase SQL Editor, then deploy the matching backend before
shipping this mobile build. The deployed API must return `401` rather than `404`
for unauthenticated requests to both `/api/v1/auth/account/deletion-context` and
`/api/v1/auth/account`.

Before production release, configure these backend environment variables in Render:

- `APPLE_CLIENT_ID` — the native iOS Sign in with Apple client identifier
  (`online.trimit.app` for the current app configuration);
- `APPLE_TEAM_ID`;
- `APPLE_KEY_ID`;
- `APPLE_PRIVATE_KEY` — the full Apple `.p8` private key, stored as a multiline
  value or with literal `\\n` line breaks.

Apple-linked deletion deliberately fails safely when this server configuration
is incomplete; it must not silently delete the local account while leaving the
Apple authorization active.

## Role model

Roles are no longer presented as three equal choices during normal signup.

### Customer

A new person authenticating for a customer action receives the customer role automatically. Customers can browse and book without completing a universal role form.

### Salon owner

Owner onboarding is an explicit action from the profile area. It creates an owner intent, authenticates when required, activates the owner workspace, and then enters salon setup. Owner payment and UPI details are collected later where they are relevant, not during authentication.

### Employee

Employee access is invitation-only. An employee enters through the employee-access action, authenticates, provides the invited phone number when required, and is admitted only after the backend validates a pending invitation.

The old universal complete-profile screen was replaced with the restricted employee invitation flow in `src/screens/auth/CompleteProfileScreen.tsx`.

## Booking contact and slot safety

`src/screens/customer/BookingScreen.tsx` now requires a confirmed, valid Indian contact number before the app requests availability or permits time-slot selection.

This ordering is intentional:

1. authenticate the customer;
2. confirm or update the booking phone number;
3. fetch current availability and prices;
4. allow the user to choose a slot;
5. continue with the existing hold and booking process.

Editing the contact number clears the selected slot and any local booking hold so stale data cannot continue into checkout.

## Native launch splash

The legacy full-screen splash layout was replaced with the modern `expo-splash-screen` configuration for both iOS and Android. It uses the existing transparent TrimiT T asset on exact OLED black in both light and dark appearance. The native image canvas is constrained to 200 points instead of being stretched across the launch screen, reducing the visible mark to approximately half of its previous size.

The shared background and native image-width values live in `src/config/splash-branding.json`. Both `app.config.js` and the JavaScript fallback splash read that configuration, preventing the native launch screen and React Native handoff from drifting to slightly different blacks. Running Expo prebuild regenerates the iOS launch storyboard/assets and Android 12 splash resources from this definition.

## Redesigned introduction screens

`src/screens/auth/OnboardingScreen.tsx` was redesigned around the new product journey and the core promise that TrimiT gives people their time back. The three screens now explain:

- avoiding uncertain walk-in queues by discovering and planning before leaving;
- choosing a salon, service, and currently available booking slot;
- exploring salons, beauty parlours, and unisex options, then comparing services, prices, reviews, and available slots.

The first visual is an accessible, full-surface tap-to-flip time composition. Its front focuses on planning before leaving, and its contrasting brand-colored reverse explains the concise `Find → Plan → Go` journey.

Every slide has its own visual language instead of reusing a generic card list. The first uses an interactive clock, the second uses a calendar and time-slot composition, and the third presents salon, beauty-parlour, and unisex choices with a comparison summary. Supporting copy was shortened so each screen communicates one customer benefit at a glance.

Each visual has purposeful entrance motion: the time scene focuses into place, the calendar rises into view, and salon choices shift horizontally into position. Animations run only for the active slide, reset when it leaves the screen, and become immediate when the device's Reduce Motion setting is enabled.

All three primary hero scenes use the same neutral `surfaceSecondary` background. The first scene's user-triggered reverse intentionally switches to the exact active-theme `primary` token so the flip is visibly different without introducing a near-match color. Onboarding uses the primary TrimiT accent for selections and emphasis; the previous green roles-card treatment was removed. Pagination uses two compact dots and one wider active capsule instead of three full-width progress bars.

The onboarding header now uses the production transparent TrimiT logo asset without a decorative logo container. The duplicate safe-area wrapper was removed, fixing the oversized top gap on notched iPhones. Screen width, content width, typography, visual height, card width, and footer sizing are derived from the live window dimensions, with compact-phone and tablet layouts plus a centered maximum content width.

All onboarding surfaces, borders, gradients, typography, spacing, radii, shadows, and semantic colors are sourced from the centralized theme. A single onboarding geometry helper defines the hero and nested panel curves, preventing unrelated corner radii from appearing in the same composition. The screens therefore support light and dark appearance without screen-specific hard-coded presentation colors.

Onboarding completion is intentionally persisted in device storage, so a person sees the introduction only once after installation. Debug builds include a `Replay introduction` action under `Account & support` or the signed-in profile's `Developer preview` section. This action resets only the onboarding flag; it does not delete the user, token, or other application data. The action is excluded from release builds.

## Guest interface polish

- The out-of-service-area state uses separate discovery and launch-notification cards with clearer hierarchy.
- The nearest-city message hides impractical long-distance estimates while still naming the nearest live TrimiT city.
- The launch form treats the visitor's name as optional and keeps email as the only required contact field.
- The guest account screen is titled `Account & support`, includes an explicit route back to Discover, and uses a full-width sign-in action.
- The Google sign-in control keeps the standard white surface and colored Google mark without the previous dark outline or shadow.
- The standalone `Profile → My offers & coupons` entry is intentionally hidden
  for 1.1.0. Its screen, route, and checkout promotion behavior remain in the
  code. A future release can restore only the profile entry by setting
  `EXPO_PUBLIC_ENABLE_MY_OFFERS=true`.

Before restoring the Offers entry, verify the header on a real notched iPhone,
empty/loading/error states, and coupon visibility/expiry for a test customer.
Do not remove or alter checkout discounts as part of this visibility toggle.

The automatic TRIMIT50 welcome popup on Discover is also paused for new and
returning sign-ins. `ENABLE_WELCOME_VOUCHER` is explicitly `false` in
`src/lib/featureFlags.ts`. The welcome lookup does not run or consume the local
shown marker while disabled, and the modal itself cannot render. Existing
grants, backend eligibility, and checkout discounts remain unchanged. Restore
this flag only in a later release after welcome-promotion QA; it is independent
of the Profile Offers entry flag.

Verbose diagnostic console output is preserved as commented code for 1.1.0.
Warnings, errors, and Sentry remain active as before. See
[Restoring debug logs safely](RELEASE_DIAGNOSTICS.md) for the exact locations,
local re-enable steps, privacy rules, and release checks.

The September follow-up fixes give the Auth native modal its own safe-area
provider and share header geometry between Login, Verify OTP, and My Offers.
The extra manual top inset on My Offers was removed. The reusable explanation
of the post-sign-in return flow is in
[`docs/architecture/post-auth-intent-restoration.md`](../../docs/architecture/post-auth-intent-restoration.md).

## Xcode and Metro development workflow

The shared iOS scheme now has a Launch pre-action that runs `scripts/ensure-metro-for-xcode.sh` whenever a developer presses Run in Xcode. Because the generated `ios/` folder is not committed, the tracked `plugins/withXcodeMetroLauncher.js` config plugin reapplies this pre-action after `expo prebuild`. The helper:

- reuses Metro when a healthy server already owns port 8081;
- otherwise opens `scripts/run-metro-for-xcode.command` in a visible Terminal tab;
- uses the Node installation configured by `ios/.xcode.env` and `ios/.xcode.env.local`;
- waits until Metro reports ready before Xcode launches the Debug application;
- fails the Xcode run with a useful message if Metro cannot start within 30 seconds.

This applies to Debug launches from the shared `TrimiT` scheme. Release and Archive builds remain self-contained and do not need Metro. If Xcode was already open while the scheme file changed, close and reopen the workspace once so Xcode reloads the shared scheme.

## Shared backend behavior used by mobile

The mobile changes depend on the backend changes in this same branch.

- Customer and owner profiles can be created without mandatory phone, gender, or UPI fields.
- Provider metadata is used to resolve a display name.
- An existing customer can activate the owner workspace only through the explicit owner flow.
- Employee role activation still requires a valid invitation.
- Existing owner and employee accounts cannot be downgraded by a customer booking intent.
- Customer phone numbers are normalized and checked for duplicates when they are supplied.
- The welcome grant is issued when a customer first supplies a valid phone number rather than requiring the phone during account creation.

Account deletion additionally depends on `database/63_account_deletion_integrity.sql`,
which makes all user-linked foreign keys cascade or detach safely.

## Release verification still required

Before submitting 1.1.0, manually verify on a real iPhone or TestFlight build:

- a guest can reach salon and service details without signing in;
- cancelling authentication returns to the previous public screen;
- Apple first-time authorization saves the name without asking for it again;
- Apple repeat authorization works when Apple does not return the name again;
- Google and email OTP create a customer and return to the requested action;
- a booking returns to the correct salon and service after authentication;
- time slots remain unavailable until the booking phone number is confirmed;
- owner entry reaches salon setup;
- employee access rejects a phone without a pending invitation and accepts a valid invitation;
- light mode, dark mode, iPhone, and iPad layouts remain usable.
- email and Google accounts delete in-app and return to the guest experience;
- an Apple-linked account shows native Apple confirmation and is removed only
  after the backend successfully revokes Apple authorization;
- the same deleted access token is rejected by protected backend endpoints;
- the public `https://trimit.online/delete-account` fallback opens from mobile.

## Important maintenance rule

Do not restore a global authentication gate or a universal role form. New protected actions must create a typed, allow-listed intent and must define how the user safely returns after authentication.
