# TrimiT Web 1.1.0 Update Notes

This document explains the web application changes introduced on the `apple-fix` branch for version 1.1.0. It is intended to help future developers and AI agents understand the guest-first marketplace, progressive authentication, role entry points, and booking return flow.

## Why this release exists

The previous web authentication flow sent unauthenticated people to a generic login page, lost some requested destinations during OAuth, and required new accounts to complete one universal profile form with role, name, phone, gender, and owner payment information.

Version 1.1.0 aligns the website with the new mobile product model:

- public marketplace discovery is available before authentication;
- customer authentication happens only when an account-based action is requested;
- the requested action survives authentication;
- customers, owners, and employees enter through different product actions instead of a universal role selector;
- provider identity information is reused rather than collected again.

## New public journey

Guests can browse the website, explore salons, and open salon and service details without creating an account. The public experience clearly explains that sign-in is needed only when the person tries to book or use a personal feature.

Signed-out visitors do not see Account, My bookings, or owner workspace destinations in either the desktop header or the mobile menu. Those destinations are rendered only after the relevant authenticated role is known; the website does not show disabled personal navigation to a new visitor.

The previous fixed two-button mobile bar was also removed from the landing page, marketplace Explore page, and public SEO discovery pages. Public pages now rely on contextual actions in the page and the compact header menu, leaving the bottom of the viewport clear for browsing content.

When a guest taps Book:

1. the website stores the salon and service identifiers in a safe pending authentication intent;
2. the guest signs in or creates an account using email, Google, or Apple;
3. a normal new account is automatically created as a customer;
4. the pending intent is consumed once;
5. the browser returns directly to the booking page for the same salon and service;
6. the customer confirms a valid contact number;
7. only then does the page load availability and permit slot selection.

The person is not returned to the generic home page after authentication.

## Routing and protected actions

The main route behavior is in `src/App.js`.

Public salon discovery remains available without authentication. Protected routes now preserve approved destinations before redirecting to login. Account protection is used for:

- booking a service;
- viewing personal bookings;
- opening the personal account;
- entering owner management;
- entering employee invitation access.

Customer booking and personal-booking routes accept authenticated customer, owner, or employee accounts so a salon team member can still make a personal booking. Owner management routes remain owner-only except for the existing employee-safe dashboard and booking-management areas.

## Safe return after authentication

`src/lib/pendingAuthIntent.js` implements the web pending-intent system using session storage.

Supported web intents are:

- customer booking;
- personal bookings;
- personal account;
- account deletion;
- owner onboarding with an allow-listed owner destination;
- employee invitation claim.

The intent:

- stores only approved action types and required identifiers;
- rejects malformed values and unknown destinations;
- expires after 20 minutes;
- survives page refreshes in the current browser tab;
- is consumed once after successful authentication;
- is removed when invalid or expired.

This prevents arbitrary redirect injection and repeated post-login navigation loops.

## Public account deletion page

`src/pages/AccountDeletionPage.js` provides the dedicated public
`/delete-account` route required for the app-store account-deletion workflow.
It is linked from the website footer and from the mobile application.

- Signed-in users can review the data impact, explicitly acknowledge that
  deletion is permanent, and delete immediately.
- Signed-out users can sign in and return to the same deletion page after email,
  Google, or Apple authentication.
- A pre-filled support email remains available for people who cannot sign in or
  no longer have the app.
- Apple-linked accounts must complete Apple's fresh confirmation in the native
  iOS flow; if attempted on the website, the backend refuses unsafe deletion and
  the page offers the support-request path.

The page is included in SEO metadata, static pre-rendering, the sitemap, and the
legal footer so it remains directly reachable without an authenticated session.

## Email, Google, and Apple authentication

The main authentication behavior is in `src/store/authStore.js`.

- A new user authenticating for a normal customer action is automatically bootstrapped as a customer.
- Apple name values are normalized whether the provider returns a string or Apple's structured given-name/family-name object.
- Provider names are saved to Supabase metadata when available.
- Google uses the same automatic customer-bootstrap behavior.
- Missing provider names do not block the user. The backend resolves the best available display value and the profile remains editable later.
- OAuth callback handling now consumes the pending intent and restores the exact approved destination.
- Email login, signup, and OTP verification preserve the same destination.
- Interrupted profile bootstrap can be retried without showing the old universal identity and role form.

The supporting pages are `src/pages/LoginPage.js`, `src/pages/SignupPage.js`, `src/pages/VerifyOtpPage.js`, `src/pages/AuthCallbackPage.js`, and `src/pages/ProfileBootstrapPage.js`.

## Role model

### Customer

Customer is the automatic role for a normal new account. No role selector, gender question, UPI question, or repeated email field is shown in the booking journey.

### Salon owner

Salon ownership starts from an explicit “List or manage my salon” action. `src/pages/OwnerStartPage.js` records an owner intent, authenticates if necessary, activates the owner workspace, and sends the owner to the appropriate setup or management destination.

All public owner marketing links now use this dedicated path instead of a signup URL containing a role query parameter.

### Employee

Employee access is invitation-only. `src/pages/CompleteProfilePage.js` is no longer a universal profile form. It is restricted to the employee invitation path and collects the invited phone number so the backend can validate the pending invitation.

The site header exposes only the dashboard and booking-management destinations that the existing backend permits for employees. Owner-only salon settings, services, subscription, notification, and bank-account routes remain protected.

## Booking contact and availability

`src/pages/customer/BookingPage.js` now asks the authenticated customer to confirm a valid Indian contact number before availability is fetched.

The order is deliberately:

1. authenticate;
2. resolve or create the customer profile;
3. confirm and save the booking contact number;
4. fetch fresh availability and pricing;
5. allow time-slot selection;
6. continue through the existing booking flow.

Changing the contact information clears the selected slot and any local hold. This reduces the chance of continuing with stale booking state.

`src/pages/customer/SalonDetail.js` creates the booking intent and explains the guest behavior before navigating to the protected booking route.

## Shared backend behavior used by web

The web changes depend on the backend changes included in this branch.

- Customer and owner profiles can be created without mandatory phone, gender, or UPI fields.
- Provider metadata is used to resolve the user's display name.
- An authenticated customer can activate owner access only through the explicit owner action.
- Employee activation still requires a valid invitation.
- Owner and employee roles are preserved when those users make customer booking requests.
- Customer phone numbers are normalized and checked for duplicates when provided.
- The welcome grant is issued when a customer first provides a valid phone number.

Account deletion depends on `database/63_account_deletion_integrity.sql`. Apply
that migration before deploying this backend so user-linked records cannot block
or outlive account deletion unexpectedly.

## Release verification still required

Before deploying the web release, verify against a configured backend and Supabase project:

- public salon and service browsing works in a signed-out browser;
- cancelling login leaves the public experience usable;
- email login, email signup, OTP, Google, and Apple return to the correct booking;
- a new booking account receives the customer role automatically;
- the contact number is required before time slots appear;
- an existing customer can intentionally start owner setup;
- employee invitation validation succeeds and fails as expected;
- direct protected URLs restore safely after authentication;
- refresh, back-button, and multiple-tab behavior do not create redirect loops;
- responsive layouts work on phone, tablet, and desktop widths.
- `/delete-account` works signed out, returns to itself after authentication,
  and deletes a non-Apple test account after explicit acknowledgement;
- an Apple-linked web attempt fails safely and displays the native-app/support
  route instead of partially deleting the account.

## Important maintenance rule

Do not reintroduce a universal signup role selector or require authentication for public marketplace discovery. Any new protected feature must use an approved typed intent and define its safe post-authentication destination.
